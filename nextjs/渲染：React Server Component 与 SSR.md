 为了避免调用多个请求降低页面性能，我们通常会一个接口获取多个数据，这样也一定程度上增加了状态管理和属性传递的复杂度

RSC 可以支持每个组件自己调接口，同时因为是服务端组件，接口请求不用额外的时间，且不会打包到客户端代码中（直接显示最终的 DOM）

如果只用 Next.js 做服务端渲染的话，性能没有极致提升，做全栈会用更好的提升，可扩容性降低

### SSR
Next.js v12 之前的 SSR 都是通过 `getServerSideProps` 这样的方法在页面层级获取数据，当成属性传递给每个组件，整个组件树在服务端渲染为 HTML，但是 HTML 是没有交互性的（non-interactive UI），客户端渲染出 HTML 后，还要等待 JS 完全下载并执行，JS 会赋予 HTML 交互性，这个阶段被称为水合（Hydration），**这里的 JS 和传统 React 项目打包的 JS 并不相同？**

缺点：
- SSR 的数据获取必须在组件渲染之前
- 组件的 JS 必须先加载到客户端，才能开始水合
- 所有组件必须先水合然后才能交互
所以通常 SSR 只用于页面初始加载，后面更新还是用 CSR

### RSC 与 SSR

每次 SSR 都是一个新的页面，状态不会保持，RSC Payload 更新是局部的

Next.js 中实现的 客户端组件和服务端组件虽然是基于 RSC 提出的用于区分组件类型的概念，但是具体实现上为了追求更高的性能，技术上是融合了 RSC 和 SSR 的（两者优势互补）
